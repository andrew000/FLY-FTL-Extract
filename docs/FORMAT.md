# What `ftl extract` 0.12.1 really does — observations from the golden files

This is not a retelling of the README. Every point below is visible in `tests/golden/**`
(generated by the real Rust binary `ftl 0.12.1`, see `scripts/gen_golden.py`) or in the
experiments described at the end. Where the behaviour was a surprise it is marked **(!)**.

## 1. What is a key

| Code | Result |
|---|---|
| `i18n.get("k", a=1)` | `k = k{ $a }` |
| `i18n.a.b()` | `a-b = a-b` — attributes are joined with a hyphen |
| `i18n.some.key_1()` | **(!)** `some-key_1` — the underscore is **not** turned into a hyphen (CLAUDE.md was wrong) |
| `i18n.only_attr()` | `only_attr` |
| `i18n("call-name")` | a key: a name from `--i18n-keys` can be called directly |
| `L("x")`, `LazyFilter("x", x=1)` | keys (the default names: `i18n`, `L`, `LazyProxy`, `LazyFilter`) |
| `i18n.get(f"dyn-{x}")`, `i18n.get("a" + "b")`, `i18n.get(key="x")`, `i18n.get()`, `i18n.get(*args)` | not keys: exactly the first positional string literal is required |
| `i18n.get("k").upper()`, `i18n.get("k")["x"]` | the key `k` (a call inside another expression) |
| `i18n.get("outer", inner=i18n.get("inner"))` | both are keys |
| `i18n_utils.get("x")`, `other.i18n.get("x")` (without `-p other`) | not keys: the root of the chain must be a name from `--i18n-keys` |
| `i18n.get("dotted.key.name")`, `i18n.get("unicode-ключ", тест=1)` | **(!)** written as is — this is **invalid Fluent** (identifier = `[a-zA-Z][a-zA-Z0-9_-]*`); python-fluent and fluent-rs will yield Junk on re-reading → the next run of the original fails with a syntax error |
| `i18n.get("k", **extra)` and `i18n.get("k", count=1)` | `k = k{ $count }` — the call without `**` wins; `**` alone gives `k = k` |
| a string in a comment/docstring | not a key |

Kwargs in the placeholder message are **sorted by name**: `zeta=1, alpha=2, mid=3` →
`{ $alpha }{ $mid }{ $zeta }`, with no spaces between placeables: `key{ $a }{ $b }`.

A file is not parsed at all if its bytes contain none of the names from `--i18n-keys` /
`-p` (a quick substring check). Consequence: `broken_too.py` with a syntax error but without
the word `i18n` does **not** produce a parse-error. `Py files count` in the statistics is the
number of files in which at least one key was found, not the number of files looked at.

## 2. Prefixes, ignore attributes, ignore kwargs

- `-p self -p cls`: `self.i18n.get("k")`, `self.i18n.attr.key()`, `self.i18n("k")` are keys;
  `self.other.get()`, `self.get()`, `obj.self.i18n.get()` are not. It works only when the
  attribute right after the prefix is a name from `--i18n-keys`.
- `--ignore-attributes` checks **only the first attribute after the root**: `i18n.set_locale()`,
  `i18n.set_locale.get("x")`, `i18n.core.anything()` are ignored; `i18n.nested.set_locale()`
  → the key `nested-set_locale`. Default: `set_locale use_locale use_context set_context`.
- `-i X` **replaces** the default: after `-i core` `i18n.set_locale("uk")` becomes the key
  `set_locale`. `-I X` appends.
- `-k LF` replaces the default names (then `i18n.get(...)` is not a key), `-K` appends.
- `--ignore-kwargs when`: the kwarg simply does not make it into the placeholder (`dialog-title{ $name }`).
- `_path="wallet/balance.ftl"` → `<lang>/wallet/balance.ftl`; `_path="wallet"` (no
  extension) → `wallet/_default.ftl` (precisely: `<_path>/<default-ftl-file>`); `_path=""`
  → the default file. `_path` is not a message kwarg.

## 3. File format

- `key = value` without alignment; every entry ends with `\n`.
- The order of kept entries = their position in the existing file. New keys are appended **at
  the end** in **hash order** (iteration of an `FxHashMap`, see section 7), neither
  alphabetically nor in order of appearance in the code.
- A commented-out key: the serialized entry, every line prefixed with `# `, wrapped in blank
  lines on both sides (a blank line before, unless it is the first entry of the file, and a
  blank line after):

  ```
  hello-user = Hello, { $name }!

  # unused-key = This one is not used anymore


  # kwargs-changed = Old { $old }

  ```

  Two commented-out keys in a row → **two** blank lines between them.
- An attached comment (a `#` line right above the key) is commented out together with the key:
  `# # Attached comment on a stale key` / `# stale-with-comment = has comment`.
- Standalone comments (`#`, `##`, `###`, separated by a blank line) keep their position; when
  the file is rewritten blank lines appear around each of them (as with commented-out keys),
  so a file with `### ...\n\n## ...\n` has **two** blank lines between them after writing.
- A file holding **only comments** (`only_comments.ftl`) is not rewritten at all.
- Multi-line values, select expressions, attributes (`.title = ...`), terms (`-brand`),
  references (`{ -brand }`, `{ ref-child }`), functions (`{ NUMBER($n) }`), `{{ $inner }}`
  are serialized identically to python-fluent 0.19 `FluentSerializer` (checked on every
  golden file: parse → serialize gives byte-for-byte the same text).

## 4. Merging with existing files

- A translation is kept if the key is in the code and the set of `$variables` matches (the
  order of the variables in the text does not matter: `{ $b } and { $a }` with `a=, b=` is
  fine; `{ NUMBER($n) }` yields `n`).
- Kwargs changed → the old entry is commented out in place, a new placeholder is appended at
  the end (`updated +1`, `commented +1`, **not** `added`).
- `_path` changed → the old entry is commented out in the old file, the new placeholder goes
  to the new file (`updated +1`, `commented +1`).
- A key that is not in the code → commented out (`commented +1`), **except**: terms (`-brand`)
  are always kept; a message referenced by another kept message that is in the code
  (`ref-parent = See { ref-child }` → `ref-child` lives).
- Markers in the attached comment: `# ftl-extract: ignore stale` / `ignore all` — the key is
  not commented out; `ignore kwargs` — a kwargs mismatch is ignored; `ignore untranslated`
  has no effect on extract (the key is commented out if it is not in the code). A key with
  `ignore stale` that references another keeps that one alive too (`stale-parent` →
  `stale-child`). Case does not matter (`FTL-Extract: Ignore Stale, Kwargs`), names separated
  by a comma or a space. `# ignore` (legacy) = only `untranslated` → the key is commented
  out. `# ftl-extract: ignored` is not a marker.
- `--comment-keys-mode warn`: nothing is commented out; for every such key stderr gets
  ``[WARN  extractor::ftl] Key `x` in `locales\en\_default.ftl` is not in code (kwargs mismatch or missing).``,
  and the updated keys (new kwargs / a new `_path`) are **not added** — the old entry stays
  as it was. The `commented`/`updated` statistics are counted exactly as in `comment` mode
  (i.e. `commented: 5` although nothing was commented out). The order of the WARN lines is
  hash order.
- `--dry-run`: the files are not touched, the statistics are the same as in a real run.
- A key defined twice in one locale (in one file or in different ones) → an abort before any
  write (see the Rust sources, not reproduced in the fixtures).

## 5. Aborts and parse errors

- The same key with different `_path` (in different files or in one) or with different kwargs →
  ``[ERROR cli] Error during extraction: Extraction aborted: 3 problems found in Python sources, no .ftl files were written.``
  + one line each `  - [key-path-conflict] Fluent key shared has different paths: one.ftl and two.ftl (app\a.py:1:1, app\b.py:1:1)`,
  sorted by (key, message). Locations are `path:line:col`, col counted in characters from
  1, path as the walk built it (`app\a.py` on Windows). `--allow-parse-errors` has no effect
  on conflicts. Exit code 1. Singular: `1 problem`.
- A syntax error in a file that contains `i18n`:
  ``  - [parse-error] Failed to parse Python file: unexpected EOF while parsing (app\broken.py:3:1)``
  plus the extra line `Pass --allow-parse-errors to skip unreadable or unparseable files and continue.`
  The error text comes from the ruff parser; the EOF position is the line after the last `\n`,
  column 1. With `--allow-parse-errors`: ``[WARN  extractor::ftl] Skipping Python file: [parse-error] ...``,
  the file is skipped, and its keys (`keep-me`) are **commented out** as unused.
- Multi-line messages in the logs: env_logger adds 4 spaces to every following line
  (`      - [key-...` = 2 spaces from the message + 4 from the logger).

## 6. File walk, languages, line endings, config

- The `code-path` walk: only `*.py`; **hidden** directories/files (`.hidden/`, `.venv/`, `.git/`)
  are always skipped; a `.gitignore` **inside** the code path is honoured (`generated/`),
  rules from parent directories are not. Default exclude globs: `**/.venv/**`, `**/venv/**`,
  `**/.git/**`, `**/__pycache__/**`, `**/.pytest_cache/**`. `-e G` replaces them (then `venv/`,
  `__pycache__/` are indexed), `-E G` appends. Files are sorted by path component-wise.
- The same walk for `.ftl` in `<locales>/<lang>` (hidden files and `.gitignore`/`.ignore`
  inside).
- `-l uk -l en`: every language is processed independently; in a new language the
  translations = placeholder (`hello = hello`). Per-language statistics are printed as a
  Debug `FxHashMap`: `{"uk": 1, "en": 1}` — **hash order**, not the `-l` order.
- `--line-endings crlf|lf|cr`: applied to the whole file after serialization (including the
  kept translations); `default` = `\n`, even if the input file was CRLF. Input CRLF parses
  fine. **(!)** `cr` gives `hello = Hello\rbye = ...` — a lone `\r` is not a line end in
  Fluent, so on the next run such a file is read as one message.
- `--default-ftl-file messages.ftl`: keys without `_path` go to `messages.ftl`; an old
  `_default.ftl` with the same key → the key is commented out there and added to
  `messages.ftl` (`updated: 1`, `commented: 1`, `added: 1`, `stored: 2`).
- `pyproject.toml` is searched upwards from cwd. Relative paths from the config are joined to
  the pyproject directory as an **absolute** path and printed as such: `Code path:
  C:\...\fixture\src/bot` (the `\` separator from join + `/` from the config as is). In the
  golden files this directory is replaced with `<cwd>`. `-l pl` on the CLI replaces
  `languages` from the config entirely; so does `--comment-keys-mode`.
- Statistics (stderr, env_logger without timestamps):

  ```
  [INFO  cli] Code path: app
  [INFO  cli] Locales path: locales
  [INFO  extractor::ftl] FTL Extraction completed in <t>s.
  [INFO  extractor::ftl] FTL Processing completed in <t>s.
  [INFO  cli] Extraction statistics:
  [INFO  cli]   - Py files count: 2
  [INFO  cli]   - FTL files count: {"en": 0}
  [INFO  cli]   - FTL keys in code: 22
  [INFO  cli]   - FTL keys stored: {"en": 22}
  [INFO  cli]   - FTL keys updated: {"en": 0}
  [INFO  cli]   - FTL keys added: {"en": 22}
  [INFO  cli]   - FTL keys commented: {"en": 0}
  [INFO  cli] ✅ Done in <t>s.
  ```

  `FTL files count` — the number of `.ftl` found in the language directory before writing;
  `keys stored` — the number of messages (not comments and not terms) in the files after
  merging, larger in `warn` mode because the unused ones stay messages. stdout is empty.

## 7. Hash order (why new keys come in this order)

The original keeps the keys in an `FxHashMap` (`rustc-hash` 2.1, hashbrown/SwissTable with
groups of 16, std `HashMap`). Iteration order = increasing bucket index; the bucket = the
first free slot from `hash & mask`, taking into account the insertion order and the table's
growth history (4 → 8 → 16 → 32 … buckets at 3, 7, 14, 28, … elements). The insertions go
like this:

1. a per-file map in order of appearance in the code (a repeated key does not insert);
2. rayon `fold`/`reduce`: every file is its own leaf, the tree is split in halves
   (`mid = len // 2`), `reduce(a, b)` inserts the **smaller** map into the larger one (on a
   tie — `a` into `b`); in a leaf `fold` the file's keys are inserted into an empty map in the
   iteration order of the per-file map;
3. `keys_to_add`: new and path-changed keys in the iteration order of the map from step 2,
   then the keys with a kwargs mismatch; the output is the iteration of `keys_to_add`.

This is reproduced in `fly_ftl_extract/ftl/rustorder.py` and verified on 30 runs of the
original (`tests/fixtures/rustorder_cases.json`, 1–120 keys, 1–30 files): 30/30 match. The
order **does not depend** on the number of rayon threads (checked with
`RAYON_NUM_THREADS=1,2,4,8` — the same md5), consistent with the model «every file is its own
leaf».

The same mechanism determines the order of the WARN lines in `warn` mode (the map
`keys_to_comment`, which first receives the path-changed keys, then the kwargs-changed ones,
then the unused ones in the iteration order of the map of kept keys, which itself is built
with `with_capacity(len(body))` per file and merged over the same tree) and the order of
languages in the statistics (`init_lang` in `-l` order).

## 8. Parser errors: what is reproduced, what is not

Reproduced from the golden files (fixtures `parse_error*`, `invalid_utf8`, `ftl_syntax_error`):

| Situation | Original (ruff / Rust / fluent-rs) | Our source |
|---|---|---|
| an unclosed bracket up to the end of file | `unexpected EOF while parsing` at the EOF position | `SyntaxError` «was never closed» → EOF |
| an extra indent | `Unexpected indentation` `line:1` | «unexpected indent» |
| no block after `def` | `Expected an indented block after function definition` | «expected an indented block after … on line N» without the tail |
| a character outside the grammar (`$`) | `Got unexpected token $` at the character's position | «invalid syntax» + the character at the position |
| `def (x):` | `Expected an identifier` | «invalid syntax» right after `def`/`class` |
| a latin-1 byte | `invalid utf-8 sequence of 1 bytes from index 5` (`1:6`) | `UnicodeDecodeError` → the Rust `Utf8Error` format |
| a truncated UTF-8 sequence at the end | `incomplete utf-8 byte sequence from index 18` | the same, reason «unexpected end» |
| `.ftl`: an entry without a value or attributes | `Failed to parse FTL file <path>:2:1: Expected a message field for "broken"` | the start of python-fluent's Junk + the regex `id =` |

Files with UTF-8 errors also count as «unreadable»: with `--allow-parse-errors` they are
skipped with a WARN, without it — an abort with the hint about the flag.

NOT reproduced (deliberately, approximations):

- other ruff messages (e.g. `Expected ')'`, `Unparenthesized …`) are passed through as the
  Python error text;
- other kinds of fluent-rs errors (`Expected a token starting with "="`, a select without a
  default, etc.) — the text is taken from python-fluent's annotation, the position may differ;
- `-v`: the original's debug lines (`[DEBUG globset] …`, `key "star" is called with **kwargs …`,
  `Saved locales\en\_default.ftl. 20 entries.`) are not reproduced; instead, after
  `✅ Done`, our `[DEBUG fly] …` lines with the margin of every window are printed.
- `--cache*` (Phase 6): the file's place and name as in the original (`.ftl-extract-cache/extract-<version>-v<schema>.bin`,
  `--cache-path` — a directory or a `.bin` file; `--clear-cache` without `--cache` writes the
  cache too — so does the original), but the format is ours (see CLAUDE.md, «CLI
  compatibility»); the file contents are not compatible with the original.

## 9. What our `ftl` adds after `✅ Done`

Verified by `tests/test_extract_matches_golden.py` and `scripts/compare_with_reference.py`
(31/31 runs, `docs/COMPARE.md`): everything up to and including the `✅ Done` line (timings →
`<t>`) is byte for byte as in the original, stdout is empty; on an abort (exit 1) there are no
lines of ours at all. After `✅ Done`:

```
[INFO  fly] Fly statistics:
[INFO  fly]   - Neurons online: 2935 (PN 124, KC 2597, APL 1, MBON 48, DAN 165)
[INFO  fly]   - Encoder fly-odor-6, brain cd3a9c7616718a25, puffs/trial 14
[INFO  fly]   - Files sniffed: 4 (from cache: 0, without i18n names: 2, walked: 6)
[INFO  fly]   - Candidates: 98 (keys: 29)
[INFO  fly]   - Trials: 150 (resniffs: 60, base trials per window: 1, θ 5.59 / 4.51)
[INFO  fly]   - Trials/s: 53.2 (1 process, batch 256)
[INFO  fly]   - Brain wall time: 2.818s
```

`Files sniffed` counts the files that reached the fly (an i18n name is present, UTF-8,
parses); `Candidates` — all tokenizer candidates, `keys` — positive occurrences before merging;
`Trials` — brain trials in this run (from the cache — 0). `--fly-audit` adds
`[WARN  fly::audit] …` for every difference from `reference/` and the summary
`[INFO  fly::audit] Audit: 0 differences …` / `[ERROR fly::audit] Audit: N differences …`
(exit 1). Errors of the fly itself (no connectome, no weights, weights from another fly) are
`[ERROR fly] …`, exit 2, like a configuration error.

Two behavioural differences of the interpreter that had to be removed to match the Rust
binary: click on Windows expands `*` in argv (`-E **/tests/**` became `app\tests\test_x.py`)
— disabled; Python writes `\r\n` and cp1251 into a redirected stdout — the streams are
reconfigured to UTF-8 + LF.
- A commented-out key with **a blank line inside a multi-line value**: fluent-rs writes a
  whitespace-only line as a bare `#`; python-fluent — only an empty one. In
  `comment_ftl_key` such lines are replaced with empty ones before serialization, so the
  result is the same, but the fixtures have no such case.
- The file walk: the `.gitignore` semantics are implemented by hand (`fly_ftl_extract/files.py`):
  negation, `**`, anchored patterns, dir-only. Gitignore exotica (escape sequences, `\#`),
  patterns like `./tests/*` — not checked by golden.
- The rayon-tree model (every file is its own leaf) is checked up to 30 files; for very large
  projects (files ≫ 2 × the number of threads) the original could in theory give a different
  order of new keys between machines with different core counts.
